How to load test an API from your browser

A practical starting point for measuring API response time, observed throughput, and HTTP errors with a controlled browser test.

Published October 28, 2026 · Updated October 28, 2026 · Pulse

What API load testing measures

An API load test sends a controlled set of requests to an endpoint to observe how it responds. The useful evidence is more than one “fast” or “slow” number: look at response times across the run, completed requests per second, status codes, and any rate-limit signals the API exposes.

Response time

Pulse measures the time until the browser receives response headers. This helps compare requests, but does not measure how long the entire response body takes to download.

Throughput

Requests per second describes how many responses completed over the measured run. Browser throughput depends on your device, connection, request delay, concurrency, and the API being tested.

Status codes

Successful responses, HTTP 429 rate limits, other 4xx and 5xx responses, and network failures suggest different next steps. A browser cannot always distinguish CORS errors from connectivity or server failures.

Rate-limit headers

Some APIs expose a limit, remaining quota, reset time, or Retry-After. Header names and behavior differ by provider. A browser can read cross-origin headers only when the API allows them through CORS.

A safer way to run a browser API test

  1. Choose a read-only endpoint you control. A health check or safe GET route avoids creating, changing, or deleting data while testing.
  2. Start with a small request count. Confirm the endpoint, method, authentication settings, and expected behavior before increasing traffic.
  3. Keep concurrency low at first. A worker is one in-flight request. Add a delay when you need a slower, more controlled request rate.
  4. Change one setting at a time. Compare similar runs while changing request count, workers, or delay individually. This makes results easier to interpret.
  5. Read the evidence, then stop. Inspect latency, status codes, and exposed quota headers. Stop if you see unexpected errors or reach your approved testing limit.

One browser run is a snapshot, not a production capacity guarantee. It does not account for other users, server-side work, geographic differences, connection pools, or long-running effects. Use a controlled server-side test and your provider’s policy when you need production capacity numbers.

Why CORS affects an API load test

A browser may be allowed to send a cross-origin request while being prevented from reading its response. The API needs to allow the page’s origin with its CORS response headers. To let Pulse read rate-limit headers, the API must list those headers in Access-Control-Expose-Headers. A network error in the browser does not prove the API is down; check the endpoint’s CORS policy, browser console, and server logs.

API load testing questions

Can I load test an API online for free?

Yes. Pulse runs a bounded browser test without an account. A free run allows up to 1,000 requests and 10 workers. Your browser sends requests directly to the endpoint, so its CORS policy must permit browser access.

How do I measure API response time?

Send a controlled set of requests and compare their response times. Pulse measures the time until response headers arrive, then summarizes latency across completed requests. This does not include full response-body download time.

What does HTTP 429 mean in an API test?

HTTP 429 means the server is reporting that a request was rate limited. Check the provider’s rate-limit policy and any Retry-After or quota headers. The first 429 in one browser run is not automatically a safe operating threshold.

Why does my browser API test show a network error?

The browser may block access because of CORS, connectivity issues, or a server failure. Browser JavaScript cannot reliably distinguish all of these cases, so check the browser console and the API’s server logs.

Does a browser load test prove production capacity?

No. Browser results depend on your device and network and reflect a single controlled run. Use authorized, repeatable server-side testing and the service owner’s guidelines for capacity planning.
